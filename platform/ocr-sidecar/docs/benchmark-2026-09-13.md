# Typhoon OCR benchmark — 3B v1 vs 1.5-3B (2026-09-13)

เครื่อง: RTX 3050 Laptop 6GB · Ollama 0.34 · temperature 0
ตัววัด: field-level accuracy — ฟิลด์ที่ "ต้องอ่านได้" ต่อเอกสาร (`scripts/run_ocr.py` → `EXPECT`)

## สูตรที่ใช้ต่างกัน (สำคัญ — นี่คือครึ่งหนึ่งของผลต่าง)

| | 3B v1 | 1.5-3B |
|---|---|---|
| โมเดล | `scb10x/typhoon-ocr-3b` (Qwen2.5-VL) | `scb10x/typhoon-ocr1.5-3b` (Qwen3-VL) |
| prompt | v1 default (ตอบ JSON `natural_text`) | ทางการของ 1.5 จาก model card (ตอบ markdown, ตารางเป็น HTML) |
| ขนาดภาพที่ป้อน | ตามไฟล์ (1754 / 2806 / 1087px ด้านยาว) | **resize ด้านยาว = 1800px** ตาม model card ("trained with a fixed image dimension of 1800 px") |
| เวลา/หน้า | 87–692 วิ (offload CPU) | **37–54 วิ** |

รอบแรกเราป้อนภาพขนาดไม่ตรงที่โมเดลเทรน — ส่วนหนึ่งของคะแนนต่ำในรอบแรกจึงเป็นความผิดของสูตรเรา ไม่ใช่โมเดลล้วน ๆ

| เอกสาร | 3B v1<br>clean 150dpi | 1.5-3B<br>clean 150dpi | 3B v1<br>clean 240dpi | 1.5-3B<br>clean 240dpi | 3B v1<br>photo stress¹ | 1.5-3B<br>photo stress¹ |
|---|---|---|---|---|---|---|
| 01 ใบกำกับภาษี | 64% | **100%** | 73% | **100%** | 0% | **73%** |

¹ photo stress = หน้ากว้าง ~768px + เอียง + เบลอ + noise + JPEG q58 — โหดกว่ารูปมือถือจริง (3000px+) ใช้เป็น lower bound

## ข้อค้นพบ

1. **1.5-3B ผ่านเกณฑ์ clean ≥95% แล้ว (97.4%)** และคะแนน 150dpi = 240dpi
   → เมื่อ resize เป็น 1800px ตามสูตร ความละเอียดต้นทางเกิน 150dpi ไม่ช่วยเพิ่ม
2. **ฟิลด์เดียวที่พลาดในชุด clean ทั้ง 2 ความละเอียด:** "ไทยรุ่งเรืองแอร์เซอร์วิส" →
   "ไทยรุ่งเรื่อง" (วรรณยุกต์เกิน 1 ตัว + ตัดท้าย) — near-miss ไม่ใช่แต่งใหม่
3. **failure mode "แต่งเอกสารปลอม" หายไปกับ 1.5** — ใบส่งของชุด photo stress:
   3B v1 แต่งเป็นร้านที่ฉะเชิงเทรา (ไม่มีในต้นฉบับ) / 1.5-3B อ่านชื่อร้าน ที่อยู่
   เลขที่เอกสารถูก พลาดแค่ตัวเลขเพี้ยน (02→07, 2569→2559, 09:40→08:40)
   คะแนนชุด stress ยังต่ำ แต่ **ลักษณะความผิดเปลี่ยนจาก "โกหก" เป็น "อ่านผิด"** ซึ่งตรวจจับได้
4. **ตัวตรวจเลขคณิต (`sidecar/extract.py`) ทำงานตามที่ออกแบบ** บนผล 1.5:
   - clean 01/02: ผ่าน 3/3 → เข้าระบบอัตโนมัติ
   - **photo stress 01: ผ่าน 3/3** — ตัวเลขเงินถูกครบแม้ภาพโหด
   - **photo stress 02: subtotal อ่านเป็น 238,500 (จริง 228,500) → เช็คไม่ผ่าน → `needs_review`**
     = ระบบจับ OCR อ่านเลขผิดได้เองโดยไม่ต้องมีคนเทียบ นี่คือ demo ที่ควรโชว์ลูกค้า
   - ใบส่งของไม่มียอดเงิน → ยังไม่มีเช็ค (ต้องออกแบบเช็คสำหรับเอกสาร qty-only ต่อ)
5. ความเร็ว 37–54 วิ/หน้า บน GPU 6GB — พอสำหรับงาน batch ตอนกลางคืน;
   เครื่องลูกค้าที่ VRAM พอจะเร็วกว่านี้มาก

## คำตัดสิน

- **เลือก `typhoon-ocr1.5-3b` + prompt ทางการ + resize 1800px เป็นสูตรมาตรฐาน** — ใส่ใน sidecar แล้ว
- **use case คุมต้นทุน (ตาราง+ยอดเงิน): พร้อมทำ demo ลูกค้า** — พร้อมตัวตรวจเลขคณิต
- **use case RAG เอกสารทั่วไป: พร้อมทำ demo ด้วยเอกสารสแกน/PDF** (ชุด clean)
  แต่ต้องมี resolution floor ที่ทางเข้า (reject ภาพต่ำกว่า ~1500px ด้านยาว) กันชุด stress
- งานต่อ: (a) ทดสอบกับเอกสารจริงของลูกค้า — ทุกอย่างข้างบนคือเอกสารสังเคราะห์
  (b) ออกแบบเช็คสำหรับใบส่งของ (qty × แถว) (c) ลอง `typhoon-ocr-7b` เฉพาะเมื่อลูกค้ามี GPU 16GB+
