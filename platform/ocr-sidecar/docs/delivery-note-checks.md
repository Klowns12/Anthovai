# เช็คสำหรับใบส่งของ (delivery note) — สเปกและผลทดสอบ

> โค้ด: `sidecar/extract.py` · endpoint: `POST /extract` · ทดสอบกับผล OCR จริงของ 1.5-3B (2026-09-13)

ใบส่งของไม่มียอดเงิน จึงใช้ตัวตรวจเลขคณิตแบบใบกำกับภาษีไม่ได้ แต่มีสิ่งที่ตรวจได้
และ **มีสิ่งเดียวที่ตรวจแล้วมีค่าจริงสำหรับคุมต้นทุน: เทียบกับใบสั่งซื้อ (PO)**

## ชั้นที่ 1 — โครงสร้าง (ตรวจได้จากใบเดียว)

| check | ความหมาย | จับอะไรได้ (พิสูจน์แล้ว) |
|---|---|---|
| `has_doc_no` / `has_date` | อ่านเลขที่/วันที่ได้ | — |
| `date_plausible` | ปีอยู่ในช่วง [ปีนี้−2, ปีนี้+1] (แปลง พ.ศ.→ค.ศ.) | OCR อ่าน 2569→2559 บนภาพแย่ |
| `rows_sequential` | ลำดับแถว = 1..N ต่อเนื่อง | OCR อ่านแถวหาย/ซ้ำ |
| `all_rows_have_qty` | ทุกแถวมีจำนวนที่แปลงเป็นตัวเลขได้ | — |
| `no_ambiguous_qty` | ไม่มี "4.000" (จุลภาค→จุด?) — ไม่เดา ให้คนดู | เจอจริงบนภาพแย่ |
| `all_rows_have_unit` | ทุกแถวมีหน่วย (บังคับเฉพาะใบส่งของ) | — |
| `units_recognized` | หน่วยอยู่ในคลังหน่วยวัสดุก่อสร้าง | "ก้อน"→"ค้อน" บนภาพแย่ |

## ชั้นที่ 2 — ข้อยกเว้นในหมายเหตุ

คำว่า ชำรุด / เสียหาย / แตก / หัก / ขาด / ไม่ครบ / คืน / เปลี่ยน / ค้างส่ง / รอส่ง
ในคอลัมน์หมายเหตุหรือบรรทัด "หมายเหตุ:" ท้ายใบ → บันทึกเป็น `exceptions[]`
ถ้าระบุจำนวนได้ ("ชำรุด 2 แผ่น") และเป็นคำประเภทลดจำนวน → คำนวณ `net_qty = qty − 2`

นี่คือความแตกต่างระหว่าง "ของถึงหน้างาน 40 แผ่น" กับ "ใช้ได้จริง 38 แผ่น"
ซึ่งเป็นเงินที่รั่วถ้าไม่มีใครตาม

## ชั้นที่ 3 — เทียบ PO (`expected`)

```json
{ "po_no": "PO-6909-017",
  "items": [ {"description": "อิฐมอญ 6x14x3 ซม.", "qty": 4000, "unit": "ก้อน"}, ... ] }
```

จับคู่รายการด้วยความคล้ายชื่อ (SequenceMatcher + token Jaccard, threshold 0.45)
แล้วเทียบ `net_qty` กับ `ordered` → สถานะต่อบรรทัด:

| status | ความหมาย | ตัวอย่างที่ทดสอบ |
|---|---|---|
| `ok` | จำนวนสุทธิตรงที่สั่ง | 5/6 รายการในใบ clean |
| `under` | รับสุทธิน้อยกว่าสั่ง | สมาร์ทบอร์ด สั่ง 40 รับ 38 (ชำรุด 2) → supplier ค้าง 2 แผ่น |
| `over` | รับมากกว่าสั่ง — เสี่ยงถูกเรียกเก็บเกิน | PO variant สั่งอิฐ 3,600 ส่ง 4,000 |
| `missing` | สั่งแต่ไม่พบในใบ | ภาพแย่: ชื่ออิฐถูก OCR อ่านเป็น "ริมฝาชักโครก" → จับคู่ไม่ได้ (ถูกต้องที่ไม่เดา) |
| `unexpected` | ส่งมาแต่ไม่ได้สั่ง | PO variant ตัดลวดผูกเหล็กออก → ระบบชี้ทันที |

**ไม่มี PO = `needs_review` เสมอ** พร้อมเหตุผล "ไม่มีใบสั่งซื้อให้เทียบ — ยืนยันจำนวนไม่ได้"
เพราะใบส่งของลอย ๆ ยืนยันอะไรไม่ได้เลยในเชิงต้นทุน

## ผลลัพธ์ที่ worker/UI ใช้

```json
{ "doc_type": "delivery_note", "doc_no": "DN-690912-03", "site": "...", "receiver": "...",
  "line_items": [ {"idx":6, "description":"แผ่นสมาร์ทบอร์ด 8 มม.", "qty":40, "unit":"แผ่น",
                   "note":"ชำรุด 2 แผ่น", "net_qty":38} ],
  "exceptions": [ {"row":6, "kind":"ชำรุด", "qty":2, "text":"ชำรุด 2 แผ่น"} ],
  "reconciliation": { "po_no":"PO-6909-017", "lines":[...], "unexpected":[], "all_ok":false },
  "checks": { ... }, "needs_review": true,
  "review_reasons": [ "ข้อยกเว้น แถว 6: ชำรุด 2 แผ่น",
                      "'แผ่นสมาร์ทบอร์ด 8 มม.' สั่ง 40 รับสุทธิ 38 (ขาด)" ] }
```

`review_reasons` เป็นภาษาคน ตั้งใจให้ยกไปแสดงในคิว review ได้ตรง ๆ

## ผลข้างเคียงที่ได้ฟรี

การ refactor ให้ map คอลัมน์จาก **ชื่อหัวตาราง** (ไม่ยึดตำแหน่ง) ทำให้ใบกำกับภาษี/
ใบเสนอราคาได้ `qty`/`unit` ต่อแถวด้วย และเมื่อยอดไม่ตรง ระบบบอกได้ว่า
**ผิดที่ไหน**: ใบเสนอราคาชุด photo → "รายการรวม 228,500 ≠ รวมเป็นเงิน 238,500"
= รายการถูกทุกแถว หัวยอดอ่านผิดตัวเดียว — คน review แก้ตัวเลขเดียวจบ

## ยังไม่ทำ

- จับคู่ชื่อรายการเป็น rule-based — เอกสารจริงที่ชื่อสินค้าต่างจาก PO มากจะหลุดเป็น
  `missing`/`unexpected` (ปลอดภัยแต่เพิ่มงาน review) → เสริม embedding/LLM ทีหลัง
- หน่วยแปลงกัน (ตัน↔กก., คิว↔ลบ.ม.) ยังไม่เทียบข้ามหน่วย
- ทั้งหมดทดสอบกับเอกสารสังเคราะห์ — ต้องยิงใบส่งของจริงก่อนเดโม
